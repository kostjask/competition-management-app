# App-wide UX audit and redesign plan

Reviewed 2026-11-25. This is the corrective plan for P9-UI-REDESIGN after the user rejected the current experience. Keep the Material action hierarchy and use smaller corners. Redesign the navigation, task hierarchy and forms around what each person came to do. A working flow and a passing browser assertion are separate from visual and usability acceptance.

The first pilot is available in development at `/app/__fixtures/redesign`. Use the organizer, applicant and judge tabs to compare the sample journeys. The working workspace now uses assignment-based navigation, compact preference disclosures, smaller actions and inline password controls. Appearance persists in the current browser. **Venue-aware** opens venue routes and known venue sign-in/recovery returns in Night. **Match device** follows the device everywhere. The findings below record the baseline that prompted the redesign.

## Day and Night requirements

- Define semantic tokens for canvas, raised surfaces, ink, secondary text, borders, focus, action hierarchy and each feedback state. Keep dark mode low-glare with restrained warm accents, readable control boundaries and no large bright surfaces in live work. Maintain distinguishable stage, connection, warning, draft and acknowledged states without color alone.
- Apply the resolved appearance at the document root before first paint. Let explicit Day or Night win, use the OS preference in System, and use a Night default for the live/scoring journey when no preference was saved. Persist device preference and retain it across language changes, authentication, reload and role shifts. Use native `color-scheme` and theme color for inputs, select menus, autofill and browser chrome. Keep print intentionally light.
- Test menus, native date/select affordances, account/recovery, overlays, focus, errors, offline and initial loading in both modes. Verify the transition between open portal, sign-in and intended venue route without a light flash. Give the public sites matching semantic modes while preserving artwork and localized URLs. Preserve functional server-rendered navigation without scripts.
- Set control geometry with a visible, non-overlapping focus indicator, 48–56px hit areas for primary venue actions and score controls, clear touch spacing and protection from accidental second activation. Check representative text and control/state contrast in each mode, including 4.5:1 for normal text and 3:1 for essential non-text UI boundaries. Validate actual venue devices and brightness with the judge and stage lead.

## Implementation order and review

1. **Navigation and interaction proposal.** Deliver clickable flows for organizer → event → Live, applicant → application → next task, and judge sign-in/recovery → score. Show phone and desktop for both themes. Compare a compact top-bar and a contextual rail at realistic data density. Set page composition, type hierarchy and spacing from the tasks and content. Review for first action, context, meaningful Back and dead ends before changing shared UI.
2. **Shell, access and low-glare foundation.** Implement the role and event navigation, locale/appearance controls, action/field geometry, inline password control and sign-in failure guidance. Build the fixed shell through auth, empty, loading, denied and live routes before migrating more screens. Establish the current-session sign-out contract alongside this work and implement it after the ADR decision.
3. **Venue journeys.** Redesign judge and moderator together with organization-scoped live entry, recovery and print. Prove actions remain reachable in day/night, offline and on reconnection. Rehearse with intended devices and network independently of the remaining appearance work.
4. **Organizer and studio journeys.** Redesign event discovery/setup, approvals and staff, then application/roster/entries/music/checkpoints, then schedule/scoring setup/private results. Iterate each full journey, including forms, dropdowns, filters, confirmation and recovery.
5. **Public and CMS.** Redesign studio and festival paths in tandem with the editing journey. Verify localized publication and existing registration/archive behavior using representative content. Keep each existing public release gate.
6. **Full regression and human acceptance.** Compare before/after at 320, 390, 768, 1440 and 1920 px where applicable, with portrait/landscape, 200% zoom, keyboard, screen reader, reduced motion and ET/EN/RU. Cover empty/no match, pending, retry, stale/conflict, lost response, denied, and reassignment. Run the existing behavioral suites with new task-level assertions and visual snapshots. Record task completion, errors, avoidable navigation and recurring points of hesitation with each representative role.

Each slice gets three reviews. First, walk the task as its user and check the visual order without relying on the implementation design. Next, inspect rendered controls and their pending, empty, error and keyboard states against the contracts. Finally, repeat the full task after fixes with an alternate locale, narrow viewport or Night and test what breaks when the network or role changes. The organizer, representative and venue staff review their own journeys before redesign closure.

Stop a slice from advancing when an advertised destination is unusable for the role, a primary venue command cannot be found from the first viewport, a control loses focus or covers its own label, the theme flashes a light page in the venue journey, or a recovery step obscures whether a write succeeded. Capture each reproduction and repeat the same steps after the correction.

## Evidence boundaries

This pass used the live VS Code preview's local URL for real organizer sign-in and the unassigned moderator reproduction. Isolated Chromium fixtures supplied repeatable roles, contents and state transitions. The source inventory spanned 88 TSX files and enumerated 236 button and 151 link declarations across shared, routed and fixture UI. Those are source counts. Repeated rows, roles and data create more rendered instances.

The review used Hallmark's visual and theme criteria, Impeccable's critique, shape and hardening criteria, UI/UX Pro Max's interaction rules and the bundled Web Interface Guidelines. This was a single-context audit using those criteria. Impeccable's source detector returned no findings and its own live launch failed. The repository's Chromium harness ran 50 and 63 focused scenarios across phone and desktop, with ET/EN/RU coverage. Both focused runs passed.

Every mounted screen and its control family has a proposed disposition above. The rendered sample covers representative role and state journeys. Full manual activation of every data-dependent variant, assistive-technology review, real published content acceptance and physical venue checks remain release evidence. The existing local technical delivery and the redesign acceptance tasks are tracked in the [operations roadmap](roadmap/operations.md#app-redesign-delivery-order).
