# F05 — Admin event setup and lifecycle

Target specification. Inherits [shared flow contract](../USER_FLOWS.md#shared-flow-contract-and-state-vocabulary),
[UI/recovery requirements](../UI_UX.md#shared-ui-state-and-recovery-contract) and
[evidence matrix](../USER_FLOWS.md#evidence-matrix-for-each-delivered-flow).
[Flow index](../USER_FLOWS.md) · [Delivery gates](../../DEVELOPMENT_PLAN.md).


- **Actor / prerequisites:** admin with explicit event authority; P3 registration
  transition/timezone rules before opening registration; live transitions later.
- **Entry / screens:** S05 dashboard/create/edit/setup; S06 application review.
- **Happy path:** create basic event → configure dates/venue/timezone/contact and
  application deadline → inspect setup checklist → resolve prerequisites → confirm
  opening registration → review independent approvals → close/review registration
  with agreed transition → configure entry rules separately when M3 is in scope.
  Later schedule/live/finalization actions follow ADR-003 and F07–F10.
- **Validation / permissions:** resulting date pair valid; positive limits; exact
  DST/timezone interpretation; backend validates transitions and dependencies.
  Registration opening must not require scoring templates/live schema. Updating
  a stage with the generic event endpoint is not evidence of lifecycle validation.
- **Alternate / failure:** missing checklist item links to field/section;
  referenced setup deletion fails without deleting entries; concurrent edits
  require reload/compare; denied changes never apply through hidden controls.
- **Loading / empty:** no events → create; section skeletons; unset required
  fields explicitly incomplete; failed counts never appear as zero approvals.
- **Cancel / recovery:** preserve permitted draft form; cancel lifecycle dialog
  leaves stage unchanged; do not offer event deletion without an approved policy
  and scope/history protection. Notification failures use separate retry.
- **Result / stages:** valid stored event/configuration and explicit audited
  transitions. Current enum is not permission to jump between arbitrary stages;
  proposed SCHEDULED/LIVE remains gated by P6-LIVE-MODEL.
- **Dependencies:** event/setup contracts; P3-REGISTRATION, P4-CORE/REVIEW,
  P2-EMAIL/AUDIT; later P4-ENTRY-CONFIG/P6 models.
- **Acceptance:** setup and approval achievable without SQL; checklist names
  actionable blockers; invalid transitions/cross-event mutations fail backend;
  UI always shows current acknowledged stage and correct timezone.
