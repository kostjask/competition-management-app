# F06 — Invite, onboard and remove judges/moderators

Target specification. Inherits [shared flow contract](../USER_FLOWS.md#shared-flow-contract-and-state-vocabulary),
[UI/recovery requirements](../UI_UX.md#shared-ui-state-and-recovery-contract) and
[evidence matrix](../USER_FLOWS.md#evidence-matrix-for-each-delivered-flow).
[Flow index](../USER_FLOWS.md) · [Delivery gates](../../DEVELOPMENT_PLAN.md).


- **Actor / prerequisites:** admin inviter; intended judge/moderator account;
  required event, assignable-role policy, secure tokens/email and assignment model.
- **Entry / screens:** S17 event staff list/invitation link → S03 sign-in/setup →
  S15 or S14 event landing. Additional-member variant requires exact studio scope.
- **Happy path:** choose event/allowed role/intended email → send → show acknowledged
  invitation delivery/status → inspect role/event/expiry → existing user signs in
  as intended account or new invitee completes verified setup → explicit acceptance
  → atomically consume invite, grant scope and create/reconcile matching Judge
  when applicable → open assigned workspace/readiness state.
- **Validation / permissions:** no global staff choice, public role self-selection,
  credential reset for an existing user or inactive-account reactivation. Contact
  email alone is not account identity. Acceptance verifies event/account and exact
  scope; Judge CRUD alone is not onboarding or authorization.
- **Alternate / failure:** wrong-account session offers switch; expired/revoked/
  used/superseded link offers safe resend/contact, not automatic new access;
  delivery failure has retry status; partial assignment error rolls back all writes.
  Accepted user without scoring assignment sees readiness/waiting, not empty rubric.
- **Loading / empty:** inspect busy state has no leaked token; no staff offers
  authorized invite; no assignments after acceptance clearly says who acts next.
- **Cancel / recovery:** cancel acceptance leaves invite unconsumed; pending revoke
  differs from accepted remove-access. Confirm removal, preserve scores/history,
  refresh sessions/permissions and show appropriate denied state afterward.
- **Result / stages:** target invited → accepted/expired/revoked, with separate
  membership/access active/removed; current supersession metadata is not a resend/
  revoke implementation. Invitations are not stage advances; allowed stage policy
  is P2-STAFF-MODEL, late access changes must not destroy scoring history.
- **Dependencies:** current invitation and judge clients; P2-STAFF-MODEL/INVITE/
  JUDGE-ACCEPT/OFFBOARD/EMAIL, P4-STAFF; P5-MEMBERS for studio variant.
- **Acceptance:** new/existing/wrong/inactive identities, replay/concurrency,
  disallowed roles/global scope and rollback tested; removal preserves sheets;
  no invitation secret in normal list DTO, logs or routine analytics.
